# Traduções (i18n)

O site existe em **português (pt, por omissão)** e **inglês (en)**, com [next-intl](https://next-intl.dev) 4.

## Rotas

- Todas as páginas vivem em `app/[locale]/…`. O PT mantém os URLs de sempre (`/para-chefs`); o EN fica em `/en/…` (`/en/para-chefs`). `/pt/…` redireciona para o URL sem prefixo.
- Não há redirecionamento pela língua do browser (muita gente em Portugal tem o browser em inglês); muda-se com o seletor PT/EN (`components/i18n/LanguageSwitch.tsx`). Não se grava cookie de idioma.
- `app/api/*`, `app/auth/callback` e ficheiros (`robots.txt`, `sitemap.xml`…) ficam fora do idioma.
- As server actions continuam em `app/actions.ts`, `app/dashboard/actions/*`, `app/admin/*actions.ts` (fora de `[locale]`).

## Links e navegação

| Em vez de | Usar |
|---|---|
| `import Link from "next/link"` | `import { Link } from "@/lib/i18n/navigation"` |
| `useRouter`, `usePathname` de `next/navigation` | os de `@/lib/i18n/navigation` (o `usePathname` devolve o caminho **sem** `/en`) |
| `redirect("/x")` (servidor) | `return redirectLocalized("/x")` de `@/lib/i18n/server` |
| `revalidatePath("/x")` | `revalidateLocalized("/x")` de `@/lib/i18n/server` |
| URL absoluto num email (`siteUrl("/reserva/…")`) | `siteUrl(localizePath("/reserva/…", locale))` |

Os `href` escrevem-se sempre **sem** prefixo de idioma (`/procurar`); o `Link` acrescenta-o.

## Mensagens

- `messages/pt/<área>.json` é a fonte; `messages/en/<área>.json` tem **exatamente as mesmas chaves**. Uma chave em falta no EN é erro de tipos e erro em `npm run check:i18n`.
- Uma área = um namespace: `common`, `nav`, `meta`, `enums`, `home`, `paraChefs`, `support`, `search`, `chef`, `booking`, `auth`, `account`, `dashboard`, `emails`, `legal`, `errors`.
- `emails` e `legal` não vão para o browser (ver `SERVER_ONLY_NAMESPACES` em `messages/index.ts`).
- Chaves em camelCase inglês, agrupadas por componente/página: `booking.form.submit`, `dashboard.offers.empty`.
- Formato ICU:
  - variáveis: `"Pedido enviado a {name}"`
  - plurais: `"{count, plural, one {# pedido} other {# pedidos}}"`
  - género: `"{gender, select, female {Cozinheira} other {Cozinheiro}}"`
  - rich text: `"Li e aceito os <terms>Termos</terms>"` com `t.rich("x", { terms: (c) => <Link href="/termos">{c}</Link> })`
  - chavetas literais: `'{'`
- Não partir frases em bocados para colar no JSX: a ordem das palavras muda entre línguas. Usar uma mensagem com variáveis ou `t.rich`.

### Onde ler as traduções

| Onde | Como |
|---|---|
| Server Component (página, layout) | `const t = await getTranslations("booking")` (`next-intl/server`), ou `useTranslations` num componente síncrono |
| Client Component | `const t = useTranslations("booking")` (`next-intl`) |
| Metadados | `generateMetadata({ params })` → `const { locale } = await params; const t = await getTranslations({ locale, namespace: "x" })`; canonical/hreflang com `alternates(path, locale)` de `@/lib/seo` |
| Server action | `const t = await requestTranslator("errors")` (`@/lib/i18n/server`) — devolve texto já traduzido à UI |
| Email, webhook, tarefa de fundo | `getTranslator(locale, "emails")` (`@/lib/i18n/translator`) com a língua **do destinatário**, não a do visitante |
| Idioma atual | `useLocale()` (cliente) / `await getLocale()` (servidor), tipo `Locale` de `@/lib/i18n/routing` |

## Formatação

`lib/format.ts` recebe o idioma como último argumento (por omissão `pt`): `euro(40, locale)` → `40 €` / `€40`; `dayLabel(iso, locale)`; `longDay`; `monthLabel`; `rating`; `serviceLabel`, `modeLabel`, `statusLabel`, `tierLabel`; `titledName(chef, locale)` → `Chef Marta` / `Cozinheira Ana` / `Cook Ana`; `offerPriceLabel`; `fromPriceLabel`; `unitLabel`; `weekdayInitials`. As etiquetas vêm de `messages/*/enums.json`.

Os `SERVICE_LABEL`/`MODE_LABEL`/`STATUS_LABEL` antigos ficam em PT para o admin.

## Valores guardados em português

Cozinhas (`cuisine_categories.name_pt`, `?cozinha=`), dietas (`diets.name_pt`) e línguas dos chefs (códigos `pt`, `en`…) ficam guardados como estão; traduzem-se só para mostrar: `cuisineLabel(t, nome)` e `dietLabel(t, nome)` de `lib/constants.ts` (mensagens em `search.cuisines` / `search.diets`), `languageNames(códigos, locale)` de `lib/languages.ts`. Uma cozinha acrescentada por um chef aparece como foi escrita.

## O que não se traduz

- **O que os chefs escrevem** (bio, menus, unidades à medida, respostas): mostra-se como foi escrito.
- **Admin** (`app/[locale]/admin`, `components/admin`): ferramenta interna, só em português.
- **Notificações internas** (Discord) e documentos fiscais: português.

## Textos legais

Termos, privacidade e contrato dos chefs são conteúdo longo e **versionado** (as aceitações guardam a versão/hash do texto PT). Não passam para JSON: o PT fica onde está, **byte a byte igual**, e o EN é um módulo à parte (ex.: `lib/terms.en.tsx`), com um aviso de que é uma tradução de cortesia e de que a versão portuguesa prevalece. As traduções legais devem ser revistas por um advogado antes de serem vinculativas.

## Emails

Cada email vai na língua do destinatário: `profiles.locale` (contas) ou `clients.locale` (convidados, a língua do último pedido), ambos `'pt-PT'` ou `'en-GB'` (`fromDbLocale` / `toDbLocale` em `lib/i18n/routing.ts`). Uma conta nova fica com a língua do formulário de registo (metadado `locale` no `signUp`).

## Verificações

```bash
npm run check:i18n            # chaves e {variáveis} iguais em pt e en
node scripts/check-i18n.mjs --scan [pastas]   # texto em português ainda escrito no código (heurística por acentos)
```

## Acrescentar uma língua

1. `lib/i18n/routing.ts`: juntar o código a `locales`, `LOCALE_TAG`, `OG_LOCALE`, `LOCALE_NAME`.
2. Copiar `messages/en` para `messages/<código>`, traduzir, e registar em `messages/index.ts`.
3. `lib/format.ts`: datas e `ENUMS` para a nova língua.
4. Migração: juntar o valor aos `check` de `profiles.locale` e `clients.locale`.

## Emails de autenticação (Supabase)

A confirmação de registo e a recuperação da palavra-passe são enviadas **pelo Supabase**, não por `lib/email.ts`. Os modelos estão em `supabase/templates/{confirmation,recovery}.html`, gerados com o mesmo desenho dos nossos emails e com as duas línguas (o Supabase escolhe pela metadata `locale` da conta: `en-GB` → inglês, tudo o resto → português). Os textos estão em `emails.auth.*`.

Depois de mudar os textos: `NEXT_PUBLIC_SITE_URL=https://aolume.com node --import ./scripts/test-resolver.mjs scripts/auth-email-templates.mts` e colar os ficheiros no Supabase (Authentication → Emails → Templates), com os assuntos que o script mostra.

O Supabase tem de enviar pelo SMTP do Resend (Authentication → Emails → SMTP Settings): o servidor de email próprio do Supabase só entrega a membros da equipa do projeto e poucas mensagens por hora.
